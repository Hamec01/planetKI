# PLANETKI — STAGE 1 CIVILIZATION EVENTS
## Этап 1: фундаментальные события, из которых рождается цивилизация

# ⚠️ ОБЯЗАТЕЛЬНЫЙ SOURCE OF TRUTH ДЛЯ ЭТАПА 1

Этот документ является **актуальным источником правды для геймдизайна этапа 1**.

Перед дальнейшей разработкой агент обязан **пересмотреть весь существующий код проекта** и привести его к решениям, зафиксированным здесь.

## Критическое изменение концепции

В старых версиях проекта могли остаться механики, где игрок:

- выбирает готовую религию из списка;
- выбирает готовые законы из каталога;
- переключает политический режим одной кнопкой;
- покупает абстрактные технологии / знания;
- получает здания или институты просто по достижению числа;
- выбирает культурные особенности в отдельном меню без события;
- получает готовую армию / генералов без исторического происхождения;
- использует старые UI-панели, которые противоречат новой системе.

**Всё это необходимо найти, проанализировать и удалить либо переработать.**

Главное правило:

> Игрок НЕ выбирает готовую цивилизацию из меню.  
> Цивилизация рождается из событий, решений, людей, построек и накопленной истории.

Религия, законы, институты, армия, налоги, права, форма власти, отношение к рабству и другие социальные системы должны **возникать органически через события и последствия**, описанные в этом документе.

Никакая старая механика не должна оставаться только потому, что она уже написана.

---


## 0. Цель документа

На этапе 1 игрок не должен просто строить здания и копить ресурсы.

Именно здесь цивилизация впервые отвечает на базовые вопросы:

- кто считается «своим»;
- можно ли есть человека;
- кто имеет право создавать семью;
- что такое брак;
- имеет ли женщина право согласия;
- кто наследует имущество;
- кому принадлежит земля;
- существуют ли боги;
- может ли вождь считаться священным;
- кто имеет право судить;
- что делать с убийцей;
- кто выбирает вождя;
- можно ли держать пленников;
- как относиться к чужакам;
- нужно ли хоронить умерших;
- кто получает еду во время голода;
- обязаны ли дети продолжать ремесло родителей;
- что важнее: род, племя, вера или личность.

Эти решения не должны существовать как одноразовые «+5 / -5».

Они создают **институты**, которые продолжают жить в следующих эпохах.

---

# 1. Основной принцип событий цивилизации

Каждое фундаментальное событие имеет:

- Trigger — почему оно возникло;
- Context — кто участвует;
- Player Choice — решение игрока;
- Immediate Effect — немедленный эффект;
- Cultural Trait — культурный след;
- Unlock — что стало доступно;
- Lock / Restriction — что стало сложнее или запрещено;
- Follow-up Events — будущие события;
- Long-term Evolution — во что это может вырасти через эпохи;
- Historical Memory — запись в истории народа.

Нельзя делать выборы по принципу:

> хороший вариант / плохой вариант.

Каждый путь должен иметь:
- выгоды;
- риски;
- исторические последствия.

---

# 2. Культурная память

Вместо простого «переменная = true» цивилизация должна накапливать культурные традиции.

Пример:

```text
CultureMemory
- HumanFleshTaboo
- OutsiderCannibalismAllowed
- ClanMarriage
- FemaleConsentRequired
- PolygynyAllowed
- AncestorWorship
- LeaderSacrality
- CouncilTradition
- BloodFeudAccepted
```

Чем дольше правило существует, тем сильнее его `TraditionStrength`.

Пример:

```text
FemaleConsentRequired:
value = true
tradition_strength = 73
age = 86 years
```

Попытка отменить древнюю традицию позже вызывает:
- сопротивление;
- события;
- раскол;
- реакцию религии;
- политический конфликт.

# 3. ЦЕПОЧКА: КАННИБАЛИЗМ

## EVENT-CAN-01 — Голод и мёртвый охотник

### Trigger
- сильный голод;
- умерший житель;
- запас пищи критический.

### Событие

> После трёх дней без добычи охотники принесли тело погибшего соплеменника.
>
> Старик Варн говорит:
> «Мёртвому пища уже не нужна. Живые ещё могут пережить зиму».
>
> Несколько семей требуют похоронить погибшего.
> Другие смотрят на пустой амбар.

### Выбор A — «Своих не едят. Никогда.»

Immediate:
- потеря потенциальной пищи;
- +лояльность части населения;
- при тяжёлом голоде повышается смертность.

Culture:
- `HumanFleshTaboo += strong`
- `ClanBodySanctity +=`

Unlock:
- погребальные традиции;
- будущие кладбища;
- культ предков;
- уважение к телу умершего.

Future events:
- «Первое кладбище»
- «Что делать с телами врагов?»
- «Вскрытие умершего запрещено или разрешено?»

Long-term:
- медицина может развиваться медленнее, если тела считаются неприкосновенными;
- зато сильнее похоронная культура и культ предков.

---

### Выбор B — «В крайнем случае можно есть врагов, но не своих.»

Immediate:
- будущие военные пленники / тела врагов могут давать пищу в экстремальной ситуации;
- часть населения испытывает страх;
- растёт враждебность соседей, если практика становится известна.

Culture:
- `InGroupBodyTaboo = true`
- `OutGroupCannibalismAllowed = true`

Unlock:
- ритуальный каннибализм врагов;
- событие «Сила побеждённого»;
- устрашение соседних племён.

Future:
- жрец может объявить поедание врага священным;
- генерал может использовать практику как психологическое оружие;
- соседние племена могут создать коалицию против игрока.

Long-term:
- возможна воинственная религиозная ветвь;
- сложнее дипломатия;
- легче запугивать слабые племена.

---

### Выбор C — «Если племя должно выжить — можно есть и своих.»

Immediate:
- часть голодных спасается;
- сильный удар по лояльности некоторых семей;
- страх.

Culture:
- `SurvivalCannibalismAllowed = true`
- `BodySanctity -=`

Unlock:
- кризисное решение «Использовать тела умерших как пищу».

Future:
- «Семья прячет умершего»
- «Жрец требует запрета»
- «Кто имеет право решать, чьё тело использовать?»
- «Поедание преступников»

Long-term:
- может сформироваться либо жестокая практическая культура,
  либо мощное позднее движение за запрет каннибализма.

Trigger:

- возникает конфликт двух семей.

### A. «Без согласия союз невозможен.»

Immediate:

Unlock:

- романтические союзы;

Long-term:

- сложнее использовать браки как чисто политический инструмент.

---

### B. «Решение принимает семья.»

Culture:
- `ClanArrangedMarriage = true`

Effects:
- семьи сильнее контролируют демографию;
- дипломатические браки проще;
- личные конфликты вероятнее.

Unlock:
- родовые союзы;
- брачные договоры;
- приданое / выкуп.

---

### C. «Решение принимает мужчина и её семья.»

Culture:

- ограниченные права женщин.

Effects:
- часть мужчин получает больше политической силы;
- женская лояльность может быть ниже;
- выше вероятность будущих протестных / реформаторских событий.

Future:
- «Женщины требуют права отказа»
- «Вдова требует наследство»
- «Женщина-воин»
- «Дочь вождя отказывается от брака»

---

### D. «Союзы вообще не регулируются племенем.»

Culture:
- `FreePairing = true`

Effects:
- слабее родовые договоры;
- меньше контроля над наследованием;
- выше личная свобода.

Future:
- конфликт отцовства;
- наследование;
- статус детей;
- ревность;
- формирование института брака позже.

# 60. ЦЕПОЧКА: ПРАВА ЗАВИСИМЫХ ЛЮДЕЙ

- можно ли владеть вещами;

- можно ли продать человека другому роду;
- можно ли освободить за военную службу.

- даровать свободу;
- наградить, но оставить рабом;
- освободить всю его семью;
- объявить, что хозяин сам решает.

Так может появиться институт **манумиссии** — освобождения из зависимости.

## EVENT-MIL-03 — Богатый род вооружает собственных людей

### A. Разрешить без ограничений

Unlock:

### D. Разрешить только пограничным родам

Effects:

- пограничные воеводы со временем становятся очень самостоятельными.

# 38. СИСТЕМА МНОЖЕСТВА ГЕНЕРАЛОВ

Если культура разрешает:
- родовые дружины;
- частные отряды;
- личную присягу командиру;

на карте может существовать много генералов одновременно.

Каждый генерал получает:

```text
General
- personal_loyalty
- army_loyalty
- ambition
- prestige
- clan_support
- wealth
- private_followers
- victories
- grievances
- relation_to_ruler
```

Важно различать:

- `LoyaltyToRuler`
- `LoyaltyToGeneral`

Например:

Вождь имеет лояльность армии: 42%.

Генерал Брок:
- личная лояльность к вождю: 55%;
- лояльность его дружины к Броку: 92%;
- амбиции: 81%;
- престиж после побед: 88%.

Это опасная ситуация.

# 40. МЕХАНИКА МЯТЕЖА ГЕНЕРАЛА

Генерал может поднять мятеж, если одновременно выполняется несколько факторов:

- высокая амбиция;
- низкая личная лояльность;
- высокая лояльность армии к нему;
- сильная личная дружина;
- спор с правителем;
- недовольство распределением добычи;
- поддержка рода;
- поражение / кризис центральной власти.

Мятеж не должен быть случайным попапом.

На карте реально отделяются:

- генерал;
- его воины;
- поддержавшие семьи / роды;
- возможно подконтрольное поселение.

Возможные результаты:
- гражданская война;
- отдельное племя;
- новый вождь;
- компромисс;
- вассальный воевода.

# 51. Связь трёх систем: армия, налоги, рабство

Эти системы не должны существовать отдельно.

Пример цепочки:

частные дружины  
→ генералу нужны ресурсы  
→ разрешено частное финансирование  
→ генерал получает землю / рабов / дань  
→ его экономическая сила растёт  
→ армия лично предана ему  
→ генерал требует место в Совете  
→ правитель отказывает  
→ мятеж.

Другой путь:

всеобщая воинская обязанность  
→ нет больших частных дружин  
→ военный сбор идёт в общий амбар  
→ Совет контролирует расходы  
→ генералы слабее как политические фигуры  
→ сильнее коллективные институты.

# 56. Пример цивилизационного результата

К концу этапа 1 игра может описывать общество так:

> Народ Рассвета — союз вооружённых свободных родов.
> Каждый взрослый мужчина обязан защищать племя, однако каждый род сохраняет собственную дружину.
> Воины присягают своим Воеводам, поэтому знаменитые полководцы обладают значительной политической силой.
> Военных пленников можно обращать в зависимых работников, но их дети рождаются свободными.
> Каждая семья отдаёт часть урожая в общий амбар, а Совет публично распределяет запасы между армией, строительством и резервом.

Или совершенно иначе:

> Народ Рассвета запрещает рабство и частные вооружённые дружины.
> Постоянная дружина подчиняется непосредственно вождю.
> Общие сборы назначает сам правитель, а их расход не подлежит публичному отчёту.
> Покорённые племена платят ежегодную дань и предоставляют воинов.

Обе модели должны иметь реальные преимущества, риски и собственные будущие политические кризисы.

Фундаментальная тема должна разворачиваться в 3–8 событий.

Пример права женщин:

1. Девушка отказывается от выбранного мужа.
2. Женщина хочет владеть домом после смерти мужа.
3. Способная охотница просит принять её в группу.
4. Дочь вождя хочет участвовать в Совете.
5. Женщина требует право наследовать власть.

Решения предыдущих событий меняют варианты следующих.

Если игрок уже закрепил:
`FemaleConsentRequired = true`

в следующем событии нельзя вести себя так, будто общество никогда об этом не решало.

# 61. Правило для AI

ИИ-племена должны проходить те же фундаментальные события.

Они выбирают решения из:
- культуры;
- характера лидера;
- кризиса;
- религии;
- демографии;
- предыдущих решений.

Поэтому соседний народ не получает заранее заданную «идеологию».
Его общество тоже развивается исторически.

# 64. Главный принцип этапа 1

Игрок не выбирает готовую цивилизацию в меню создания игры.

Он создаёт её поступками.

К концу этапа 1 игра должна уметь сформировать краткое описание общества, например:

> Народ Рассвета — речное племя с выборным вождём и сильным Советом старейшин.
> Они почитают предков, признают добровольный моногамный брак, допускают женщин к ремёслам и считают землю собственностью рода.
> Кровная месть запрещена: убийства рассматривает Совет.
> Чужаки могут стать полноправными членами племени после испытания.

Это описание должно быть не декоративным текстом, а результатом реальных решений игрока.

И именно эти решения переходят во второй этап.

# 66. СНАЧАЛА СОСТАВИТЬ INVENTORY, ПОТОМ МЕНЯТЬ КОД

Агент НЕ должен начинать хаотично удалять файлы.

Первый шаг — создать отчёт:

`STAGE1_CODE_AUDIT.md`

Для каждой найденной системы указать:

```text
System:
Files:
Scenes:
Current behavior:
Conflicts with approved design:
Decision:
- KEEP
- REFACTOR
- REMOVE
- MIGRATE
Risk:
Dependencies:
Tests affected:
```

Пример:

```text

ReligionSelectionPanel

Current behavior:
Игрок выбирает Solarian / Ancestor / Spirits из готового списка.

Conflict:
Религия теперь должна рождаться из EVENT-REL-01 и последующих событий.

REFACTOR underlying religion state into emergent ReligionState.

Dependencies:
MainHUD
SaveGame
AI religion picker
Localization strings
Temple menu
```

Только после такого inventory начинать изменения.

# 67. КАТЕГОРИИ РЕШЕНИЙ ПРИ АУДИТЕ

## KEEP

Система полностью соответствует новой концепции.

Пример:
- движение жителей;
- real-time карта;
- размещение зданий.

## REFACTOR

Идея нужна, но текущая реализация неверна.

Пример:
старый `LawSystem` может быть сохранён как хранилище принятых норм, но игрок больше не открывает каталог и не нажимает «принять закон».

## REMOVE

Механика больше не существует.

Пример:
- готовый religion picker;
- law shop;
- кнопка «выбрать режим»;
- абстрактное дерево науки, если оно осталось.

## MIGRATE

Данные полезны, но должны быть переведены в новую модель.

Пример:
`RELIGION_ANCESTORS`
может перестать быть кнопкой выбора и стать результатом цепочки событий.

# 68. ЧТО НЕОБХОДИМО УДАЛИТЬ ИЛИ ПЕРЕРАБОТАТЬ

## 68.1. Готовый выбор религии

Недопустимо:

```text
Религия
[Соляризм]
[Духи природы]
[Культ предков]
[Атеизм]
```

как прямой выбор из меню.

Правильно:

природное / социальное событие
→ вопрос
→ решение игрока
→ `CultureMemory`
→ формирование веры
→ открытие религиозных институтов.

Меню религии ПОСЛЕ возникновения веры может показывать:

- текущее учение;
- историю;
- жрецов;
- ритуалы;
- священные места;
- расколы;
- принятые догматы.

Но не должно позволять бесплатно заменить фундаментальную веру кнопкой.

# 69. ГОТОВЫЙ ВЫБОР ЗАКОНОВ УБРАТЬ

Недопустимо:

```text
Законы:
[Моногамия]
[Рабство]
[Свобода веры]
[Наследственная власть]
```

как каталог доступных переключателей.

Теперь закон появляется:

```text
условия мира
→ событие
→ конфликт
→ решение
→ культурная норма
→ при достаточной институционализации — закон.
```

Панель законов становится **реестром уже возникших норм и институтов**, а не магазином бонусов.

Она должна показывать:

- действующее правило;
- как оно возникло;
- год принятия;
- силу традиции;
- кто поддерживает;
- кто недоволен;
- связанные события;
- возможна ли реформа.

# 70. ФОРМА ПРАВЛЕНИЯ НЕ ВЫБИРАЕТСЯ КНОПКОЙ

Удалить / переработать UI вида:

```text
Выберите:
Монархия
Совет
Теократия
Республика
```

Форма правления должна быть **derived state**.

Пример:

```text
HereditarySuccession = true
RulerFinalAuthority = true
LeaderSacrality = high
CouncilPower = low
```

→ система выводит:

`Наследственное сакральное вождество`

Позже это может эволюционировать в монархию.

Название режима — результат состояния общества, а не исходный выбор.

# 71. НИКАКОГО АБСТРАКТНОГО TECH TREE, ЕСЛИ ОНО ЕЩЁ ОСТАЛОСЬ

Если в коде существует:

- `science_points`;
- `knowledge_points`;
- глобальная кнопка Research;
- старое универсальное tech tree;

агент обязан проверить, используется ли оно ещё.

Для этапа 1 утверждён другой принцип:

```text
работа
+ опыт NPC
+ конкретное здание
+ условия
+ событие
= открытие.
```

Примеры:

- случайно закалённый клинок → Закалка;
- тяжёлое бревно → Колесо;
- несколько смертей + лечебная практика → Лечебная хижина;
- символы / метки → ранняя запись.

Если старая research-система нигде больше не нужна — удалить полностью, включая UI, данные и save-поля.

# 72. АУДИТ РЕСУРСОВ

Проверить каждый ресурс.

Для каждого ответить:

1. Нужен ли он на этапе 1?
2. Откуда физически появляется?
3. На что реально тратится?
4. Связан ли с людьми / зданиями?
5. Не остался ли от старой концепции?

Особенно проверить старые:
- очки науки;
- вера как абстрактная валюта;
- влияние как универсальная валюта;
- старые очки законов;
- старые очки культуры.

Если показатель нужен только как статистика — он не обязан быть расходуемым ресурсом.

---

# 73. АУДИТ UI

Проверить каждый экран и кнопку.

Для каждого UI action:

```text
Does this action still exist in design?
What game state does it mutate?
Can the same state now only be changed by event?
Does it bypass prerequisites?
```

Удалить:

- мёртвые кнопки;
- старые вкладки;
- скрытые debug-переключатели, влияющие на обычную игру;
- старые панели religion/law/research;
- дублирующие интерфейсы.

Критическое требование:

**игрок не должен иметь два разных способа изменить одно и то же фундаментальное правило.**

Например нельзя:

- принять моногамию событием;
- а затем в старом меню переключить на полигамию бесплатно.

# 74. НОВАЯ АРХИТЕКТУРА СОСТОЯНИЯ ЦИВИЛИЗАЦИИ

Нужно иметь единый authoritative state.

Рекомендуемая структура:

```text
CivilizationState
- culture_memory
- institutions
- religion_state
- government_state
- military_state
- economy_state
- social_state
- discovered_practices
- historical_events
```

Системы UI НЕ должны хранить собственную отдельную истину.

UI только читает состояние и отправляет допустимые команды.

# 75. CULTURE MEMORY ДОЛЖНА БЫТЬ AUTHORITATIVE

Пример:

```text
CultureMemoryEntry
- id
- value
- strength
- established_year
- source_event_id
- supporters
- opponents
- reformable
```

Это позволяет ответить:

- что принято;
- почему;
- когда;
- насколько укоренилось;
- можно ли изменить;
- какие события от него зависят.

# 76. ВЗАИМОИСКЛЮЧАЮЩИЕ РЕШЕНИЯ

Нельзя хранить противоречивые bool без правил.

Плохой пример:

```text
Monogamy = true
Polygyny = true
UnregulatedUnions = true
```

Нужно использовать exclusive groups.

Пример:

```text
MarriageStructure:
- UNDEFINED
- MONOGAMY
- POLYGYNY
- POLYANDRY
- UNREGULATED
```

А отдельные параметры:

```text
MarriageConsent:
- NONE
- FAMILY
- INDIVIDUAL
- MIXED
```

Так система не попадёт в невозможное состояние.

# 77. ПРОВЕРИТЬ ВСЕ EXCLUSIVE GROUPS

Минимум:

- структура брака;

- система наказаний.

Некоторые системы допускают смешанные варианты, но это должно быть явно спроектировано.

# 79. EVENT CONDITIONS НЕЛЬЗЯ ДУБЛИРОВАТЬ ПО UI

UI не решает, можно ли событие запустить.

Единственный источник:

`EventEligibilityService`

или аналогичная централизованная система.

Иначе появятся баги:

- UI считает событие доступным;
- симуляция считает недоступным;
- AI видит третье состояние.

---

# 80. СОБЫТИЯ ДОЛЖНЫ БЫТЬ IDEMPOTENT

Если событие уже применило решение, повторный вызов не должен повторно:

- открыть то же здание;
- дважды начислить trait;
- создать двух одинаковых должностных лиц;
- второй раз сменить институт.

Каждый effect должен проверять текущее состояние.

---

# 81. ЗАЩИТА ОТ ОДНОВРЕМЕННЫХ СОБЫТИЙ

В real-time игре возможна ситуация:

в один tick выполняются условия двух событий одной цепочки.

Нужно предусмотреть:

```text
chain_lock
event_queue
priority
```

Пример:

нельзя одновременно показать:

- «Кому присягает воин?»
- «Частные дружины»
если базовая военная модель ещё не определена.

---

# 82. СОБЫТИЯ НЕ ДОЛЖНЫ СПАМИТЬ

Проверить:

- global cooldown;
- category cooldown;
- chain cooldown;
- NPC cooldown;
- building cooldown;
- region cooldown.

Фундаментальные события должны быть редкими и значимыми.

Игрок не должен получать пять общественных революций за одну игровую неделю.

---

# 83. ПРОВЕРКА FOLLOW-UP ЦЕПОЧЕК

Агент должен построить dependency graph событий.

Для каждой цепочки найти:

- orphan events;
- impossible events;
- circular dependencies;
- events without triggers;
- unlock без потребителя;
- building без способа открытия;
- law без исходного события.

Желательно создать debug-команду:

`ValidateEventGraph()`.

---

# 84. РЕЛИГИОЗНЫЕ ПРОТИВОРЕЧИЯ

Проверить кейсы:

### Случай 1
Игрок выбрал ранний рационализм.

Не должен автоматически существовать:
- обязательный жрец;
- государственное святилище;
- жертвенный ритуал.

Они могут появиться позже только через новые исторические события.

### Случай 2
Есть культ предков.

Это не означает автоматически:
- монотеизм;
- политеизм;
- профессиональное духовенство.

### Случай 3
Вождь = верховный жрец.

Если позже общество отделяет религию от власти:
- статус должен корректно мигрировать;
- UI должен обновиться;
- старые бонусы должны исчезнуть.

---

# 85. ПРАВОВЫЕ ПРОТИВОРЕЧИЯ

Примеры багов, которые необходимо исключить:

- рабство запрещено, но UI позволяет купить раба;
- военный пленник автоматически становится рабом при `SlaveryForbidden`;
- добровольный брак включён, но событие насильно выдаёт персонажа замуж без конфликта;
- земля коллективная, но частный собственник продаёт участок без соответствующего института;
- смертная казнь запрещена, но стандартная кнопка «казнить» всё ещё доступна;
- частные дружины запрещены, но NPC-генерал автоматически создаёт личную армию.

# 86. АРМИЯ — ПРОВЕРИТЬ ПРОИСХОЖДЕНИЕ КАЖДОЙ ВОЕННОЙ СИСТЕМЫ

Не должно быть готового «Recruit General», если общество ещё не создало такую должность.

Генерал появляется:

- через Штаб Воеводы;
- через назначение;
- через военное событие;
- через проявившего себя бойца.

Проверить:

- кто может быть генералом;
- кто имеет войска;
- кому они лояльны;
- кто их содержит;
- разрешены ли частные дружины;
- разрешена ли всеобщая служба;
- что происходит с профессией NPC после мобилизации.

# 87. МЯТЕЖ ГЕНЕРАЛА — НЕ RANDOM EVENT

- рост личной дружины;
- требования генерала.

Это предотвращает ощущение несправедливого RNG.

# 88. НАЛОГИ / ОБЩИЕ СБОРЫ — НЕ ПОЯВЛЯЮТСЯ ИЗ НИОТКУДА

- работа на общее дело.

# 100. EDGE CASES, КОТОРЫЕ НУЖНО ПРОВЕРИТЬ

1. Умер единственный персонаж, необходимый событию.
2. Вождь умер во время открытого modal event.
3. NPC одновременно назначен кузнецом и генералом.
4. Здание разрушено, пока его event находится в очереди.
5. Племя проиграло войну до решения вопроса о пленниках.
6. Рабство запрещено после того, как зависимые люди уже существуют.
7. Частные дружины запрещены, когда у генералов уже есть армии.
8. Религия реформирована во время активного религиозного события.
9. Save сделан между event trigger и player choice.
10. Два follow-up event хотят изменить один exclusive group.
11. AI и player одновременно претендуют на один объект / пленника.
12. Налоговая система отменена, но казначей остаётся назначенным.
13. Совет распущен, но `CouncilBudgetOversight` активен.
14. Вождь одновременно умер и был свергнут.
15. Генерал поднял мятеж в момент внешнего боя.
16. Пленный стал членом племени, но старый slave flag не снят.
17. Ребёнок взрослеет при изменившемся наследственном законе.
18. Дерево event dependency содержит цикл.
19. Event unlock открывает уже уничтоженное / недоступное здание.
20. UI показывает старое значение после выбора.

---

# 101. НЕ ДОПУСКАТЬ «ПОЛУМИГРАЦИИ»

Самая опасная ситуация:

- половина игры уже event-driven;
- половина всё ещё old menu-driven.

Это создаст невозможные комбинации.

Поэтому после каждого subsystem migration:

1. новый путь должен быть полностью рабочим;
2. старый пользовательский путь должен быть выключен;
3. данные должны иметь один authoritative owner.

# 104. НИКАКИХ ТИХИХ FALLBACK

Если событие требует:

- персонажа;
- здание;
- институт;

а объект отсутствует — нельзя молча выбрать случайную замену без правила.

Система должна:

- отменить event;
- reroute на предусмотренный fallback;
- записать debug warning.

# 106. UI ДОЛЖЕН ОБЪЯСНЯТЬ ПРИЧИНЫ

Игрок должен понимать, почему возникла ситуация.

- его род контролирует 28% военной силы;
- он недоволен последним разделом добычи.

Не показывать скрытые RNG проценты, если это ломает атмосферу, но причинность должна быть понятной.

# 107. ДОЛГОСРОЧНАЯ СОВМЕСТИМОСТЬ С ЭТАПАМИ 2–5

При удалении старого кода не создавать тупики.

Stage 1 state должен переходить дальше.

```text
CouncilTradition
```

- городской совет;

- парламентскую традицию.

```text

```

может стать:
- феодальными дружинами;
- частными армиями;
- военной знатью.

```text

```

может стать:
- казначейством;
- бюджетным контролем;
- парламентским бюджетом.

Поэтому удаляем старые готовые режимы, но сохраняем **эволюционные корни**.

# 108. FINAL ACCEPTANCE — КОГДА МИГРАЦИЯ ЭТАПА 1 СЧИТАЕТСЯ ГОТОВОЙ

Миграция считается законченной только если:

- нет прямого выбора готовой религии;
- нет прямого каталога готовых законов;
- нет прямого выбора формы правления;
- нет старого абстрактного исследования, если оно больше не используется;
- фундаментальные нормы возникают через события;
- события проверяют реальные условия;
- решения сохраняются в `CultureMemory`;
- противоречивые состояния технически предотвращаются;
- специальные здания открываются причинами;
- апгрейды зданий открываются действиями / событиями;
- AI следует тем же правилам;
- генералы имеют историческое происхождение;
- налоги эволюционируют из ранних сборов;
- рабство / его запрет реально влияет на симуляцию;
- UI не предоставляет обходных старых путей;
- сохранение корректно хранит новые состояния;
- нет dangling references на удалённые системы;
- полный этап 1 можно пройти несколькими принципиально разными цивилизационными путями.

# 109. ГЛАВНОЕ УКАЗАНИЕ АГЕНТУ

Не пытаться «прикрутить» новую систему поверх старой.

Нужно:

**проанализировать → классифицировать → мигрировать → удалить старое → протестировать → только затем идти дальше.**

Если существующая реализация противоречит этому документу, приоритет имеет этот документ.

Если агент находит конфликт, который документ не определяет однозначно:

1. не придумывать фундаментальное решение самостоятельно;
2. описать проблему;
3. показать варианты;
4. указать последствия каждого;
5. остановиться на границе спорного изменения.

Главная задача — получить чистый фундамент, а не сохранить максимальное количество старого кода.
